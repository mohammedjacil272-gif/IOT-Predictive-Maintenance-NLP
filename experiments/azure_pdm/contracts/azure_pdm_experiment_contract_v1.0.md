# Azure PdM Experiment Contract v1.0

Status: Finalized for review

This contract records the final Phase 3.5 user approvals. Approval of this contract does not authorize implementation, data processing, training, inference, or predictive-performance claims.

## 1. Objective and scope

The experiment will evaluate a leakage-controlled 24-hour component-failure forecasting design on the acquired Microsoft Azure PdM simulated benchmark. The scope is limited to telemetry, benchmark-static machine metadata, and structured event records. No genuine technician narratives are present.

Failure records are target-construction inputs only. They must never be supplied as model features.

## 4. Timestamp and availability policy

Telemetry timestamps are accepted as benchmark observation times solely because the user approved the `benchmark` policy. This does not establish when data was ingested, published, or available in a real operational system.

The event tables do not contain `available_at` or equivalent detection/ingestion metadata. Event occurrence time must not be substituted for availability time. Error and maintenance events therefore remain ineligible as prediction features unless independent availability evidence is supplied.

The timestamp values remain timezone-naive. Temporal operations may use their within-dataset ordering and explicit elapsed differences, but no timezone interpretation may be added.

## 5. Target construction

For each machine and prediction anchor `t`, collect validated failure records satisfying:

```text
t < failure_time <= t + 24 hours
```

Target mapping:

- No recorded failure in the interval: `none`
- One distinct failed component: `comp1`, `comp2`, `comp3`, or `comp4`
- Two or more distinct failed components: `multi_failure`

Simultaneous failures of different components map to `multi_failure`. Multiple failures of the same component at different times remain one component class for that anchor.

Target construction must be machine-specific, timestamp-sorted, and based on an explicit elapsed-time interval join or equivalent search. Global row-based `bfill` is prohibited.

Duplicate records with the same machine, component, and timestamp remain an audit failure and must not be silently deduplicated. Missing or ambiguous machine IDs, timestamps, or component values must be excluded from target construction and reported. A missing failure record means no recorded failure evidence; it does not establish machine health.

No labels are generated by this contract-finalization task.

## 6. Feature and prediction policy

The validated telemetry contains 876,100 rows for 100 machines over `2015-01-01T06:00:00` through `2016-01-01T06:00:00`. The report found no duplicate telemetry keys or invalid numeric values. The source rows are not globally ordered, so temporal processing must sort within machine by timestamp.

Draft feature windows:

- 3-hour lookback/resampling candidate: captures recent operating behavior and is consistent with the historical Microsoft notebook approach.
- 24-hour lookback candidate: captures daily behavior and variability.

These are lookback windows, not the 24-hour target horizon. Any rolling feature must use only data available at or before its anchor and must be defined using explicit elapsed time rather than an unexplained row count.

Recommended prediction cadence: 3 hours. This matches the historical feature cadence while retaining useful resolution over hourly telemetry. The cadence remains subject to implementation review.

Candidate static machine metadata:

- `model`
- `age`

The source does not document whether these fields change over time. They may be treated as benchmark-static only, with that limitation recorded.

## 8. Chronological splitting and embargo

The verified telemetry coverage is exactly 365 days:

- Coverage start: `2015-01-01T06:00:00`
- Coverage end: `2016-01-01T06:00:00`
- Nominal 60% cutpoint: `2015-08-08T06:00:00`
- Nominal 80% cutpoint: `2015-10-20T06:00:00`

Nominal global chronological partitions:

- Training: start through the 60% cutpoint
- Validation: 60% through the 80% cutpoint
- Test: 80% through the coverage end

Operational embargo windows:

- First boundary embargo: `2015-08-08T06:00:00` through `2015-08-09T06:00:00`
- Second boundary embargo: `2015-10-20T06:00:00` through `2015-10-21T06:00:00`

Rows in embargo windows are excluded from partition use. The nominal cutpoints preserve the approved 60/20/20 time-coverage definition; the embargo intentionally reduces usable rows around boundaries. If the maximum feature lookback expands beyond 24 hours, the embargo must be recalculated before implementation.

All machines are split by the same global time boundaries. No random row split is permitted. Machine/time windows must not be duplicated across partitions.

## 9. Leakage controls

- Failure targets are constructed separately from features.
- Failure records never enter the feature matrix.
- Event occurrence time is never used as event availability time.
- Error and maintenance events remain excluded while availability is unknown.
- Rolling features are causal and machine-specific.
- Target intervals are explicit elapsed-time intervals.
- Duplicate and ambiguous failure records are surfaced as audit failures.
- All learned preprocessing is fitted on training data only.
- Categorical vocabularies and encoders are not fitted using validation or test rows.
- Split boundaries use a 24-hour embargo for the current 24-hour lookback/horizon policy.
- No cross-machine fill operation is permitted.

## 10. Missing-data policy

| Condition | Required handling |
|---|---|
| No event recorded | Treat as no recorded event only when the eligible event stream is observable for that interval. |
| No matching event-table row | Do not interpret as proof that no event occurred. |
| Event availability unknown | Exclude the event from prediction features. |
| Missing telemetry measurement | Preserve as missing; do not silently forward-fill. Any imputation must be training-fitted and reported. |
| Missing machine metadata | Do not invent values. Exclude or use approved training-fitted imputation. |
| Missing failure record | No target evidence; do not infer health. |
| Duplicate failure record | Audit failure; do not silently deduplicate. |
| Ambiguous failure record | Exclude from target construction pending resolution. |

## 11. Evaluation metrics

Primary metrics:

- Macro F1.
- Per-class precision, recall, and F1.
- Per-component recall.
- `multi_failure` precision and recall.
- Balanced accuracy.
- Confusion matrix.
- Suitable one-vs-rest PR-AUC where class support permits.

Required baselines include the majority-class and no-failure baselines. Accuracy must not be the sole metric.

Metrics must be reported on the chronological test partition and, where support permits, by component and machine group.

## 12. Limitations and blocked components

- Event availability is absent for errors and maintenance.
- Event timestamp semantics are not documented as occurrence, detection, recording, or ingestion time.
- Timezone semantics are absent.
- Machine metadata validity over time is undocumented.
- Failure records represent recorded failure events, not necessarily complete failure history.
- The dataset is simulated benchmark data and cannot support production performance claims.
- No genuine technician narratives exist.
- Structured event NLP remains blocked until availability evidence is supplied.
